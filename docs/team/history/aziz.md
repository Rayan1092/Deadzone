### Version 2 contracts (posted before implementation)

1. **Quiet preload (`p2/quiet-preload`):** `POST /api/plan?check=false` validates/saves and broadcasts only `plan_state`, returns `{saved:true,plan_id:"P-1",checked:false}`. DEMO.md preload uses the query toggle.
2. **Gemini briefing (`p2/gemini-briefing`, implemented; dry run pending):** existing `GET /api/report` and screen `report` retain `{text,generated_at,source:"gemini"|"local"}`. Enable with `DZ_GEMINI=1`; load ignored `server/.env` (`GEMINI_API_KEY`), process env wins. Default model `gemini-3.8-flash` (official API docs verified Nov 7), configurable `GEMINI_MODEL`. One 10-second deadline for the complete exchange. Only read-only tools `get_robots`, `get_survivors`, `get_routes`, `get_network`, `get_faults`, `get_events(since)`, `get_coverage`, over an immutable request-time Command snapshot. Network means delivered relay announcements and receipt paths/counts, not live links/queues/RSSI. Events are a bounded Command receipt journal, not `Sim.events`. No truth/robot-control tool exists. Plain spoken-ready briefing; missing key, timeout, quota or malformed response uses existing deterministic local report with `source:"local"`.
3. **Phone Ask (`p2/gemini-ask`, implemented; phone UI/dry run pending):** `POST /api/ask` body `{question:"where should team 2 go?"}` (trimmed, 1-1000 chars), response `{text,generated_at,source:"gemini"|"local"}`. Same `DZ_GEMINI=1`, tools, snapshot, 10-second deadline and fallback rules as briefing. No dispatch/robot commands or screen-wide question broadcast. With unavailable Gemini return a clearly labelled Command-only local response, never pretend Gemini answered. UI provides its own pending state and displays `source`. Backend only; Yusuf owns phone box/speech.
4. **Aftershock (`p2/aftershock`, implemented; UI/reactions dry run pending):** gated by `DZ_AFTERSHOCK=1`, director `control {action:"director",value:{do:"aftershock",at:[x,y],relay:"RL1"}}`; coordinates/relay optional, default deterministic area around the first powered non-phone relay (or [22,15] when none), and that relay is destroyed if present. Explicit invalid IDs/positions fail atomically. Reality adds dynamic rubble and a short concrete wall, updates occupancy/radio loss immediately, marks relay `{destroyed:true,on:false}`; cannot power/move it back on. Destruction drops that relay's custody queue and partial hops; other custodians retain bundles and Dijkstra reroutes naturally. Events (screen/Reality only): `aftershock {at,rubble,walls,destroyed_relay,lost_bundles}`, `relay_destroyed {id,pos,lost_bundles}` and normal link/rubble events. Existing screen hello refresh carries rubble; new walls use `hello.floorplan.dynamic_walls` (separate from public `walls`) so the current Command inset cannot accidentally draw truth walls. Each new wall has `{id,a,b,material:"concrete",dynamic:true}`. `Sim.aftershock(at=None, relay=None)` is the backend hook; Rayan should observe IO, not call this from robot policy. Yusuf: reserve A for aftershock only when the toggle is enabled and draw dynamic_walls in Reality only. Prior and Command maps/relays remain unchanged until ordinary delivered observations; no director event reaches phone or Gemini. Robots react only to IO lidar/collision/radio changes; no synthetic robot state mutation. Reset removes damage. Yusuf chooses a free key for this director value; no key reserved by backend.
5. **FEC (`p2/reed-solomon`, implemented; dry run/display pending):** `DZ_FEC=1` enables real RS(255,223), 32 parity bytes and CRC verification on actual serialized payloads for up links -88 <= RSSI <= -80 dBm. Seeded per-network deterministic byte corruption; coded wire bytes count against shared bandwidth. No custody acknowledgement on decode/CRC failure, sender retries. `tick.reality.links[]` adds per-tick `corrupted_bytes`, `corrected_bytes`, `fec_failed_blocks` (zero when idle/disabled) and `fec` reflects actual enabled weak-link coding. Command/phone gets no live repair/link stats. Feature off preserves Version 1 transport/timing. Tests include correctable and uncorrectable blocks plus end-to-end delivered payload equality.
6. **CRDT (`p2/plan-crdt`, implemented; UI/dry run pending):** `DZ_CRDT=1` exposes opt-in operation merge alongside existing whole-plan edits. Per-plan epoch plus per-field logical `(counter,client)` stamps, deterministic client tie-break, region tombstones; polygons are atomic fields so concurrent point edits never invent malformed polygons. `GET /api/plan-sync?plan_id=P-1` returns `{epoch,plan,ops}`; `POST /api/plan-sync` accepts `{epoch,plan_id,ops:[{client,counter,target,field,value}]}`. Targets `plan`, `zone:<id>`, `no_go:<id>`; fields limited to plan budget / supported region fields / `deleted`. `PUT /api/plan-sync` seeds a validated SearchPlan and returns a fresh epoch. Operations merge into bounded per-field registers; duplicates/order commute for valid client clocks. Response adds `{valid,issues}` to `{epoch,plan,ops}`. If individually valid concurrent operations produce an invalid whole plan (e.g. both remaining zones deleted), the converged candidate is retained with `valid:false` and issues; it is not published as plan_state, and checks/dispatch return 409 plan_conflict until resolved. Valid candidates save and broadcast normal plan_state. All planner phones also receive `plan_sync` with the complete merge state. No operation is silently dropped to make a plan appear valid. Dispatched IDs are immutable; reset/whole-plan replacement invalidates epochs (409 sync_epoch). GET ops are current winning registers (not an unbounded log); max 1024 registers, 256 operations per batch. Client counters are persisted Lamport integers 1..2^53-1, advanced past observed counters; same counter/client/field with different values is 409 sync_clock. PUT reseeds an epoch intentionally; other clients GET/rebase pending edits, never automatically reseed on reconnect. Offline persistence/operation queues and reconnect UI are Yusuf-owned. Existing `plan_edit` may invalidate that plan's CRDT epoch, so clients resync before entering offline mode. No silent offline dispatch or safety approval.
7. **Rescue order (`p2/rescue-order`, implemented; phone UI/dry run pending):** gated `DZ_RESCUE_ORDER=1`; `GET /api/rescue-order` returns `{generated_at,source:"command",survivors:[{survivor,by,length_m,risk,reasons,reported_t}]}` from delivered routes joined to delivered survivors only. Risk is an explicit route heuristic, not medical triage: high for a delivered-map obstacle, public prior hazard on the sampled route, or reported clearance <0.25 m; medium for unknown/clearance <0.5 m or route source age >60 sim seconds; low otherwise. Sample route segments every <=half a grid cell. reasons is an array of stable string codes documented in RESCUE-ORDER.md. Age uses the delivered route source t, not live route recomputation. Sort low/medium/high risk then length then survivor ID. Omit survivors without delivered routes, use no live robot/truth hazards, and never alter route data. UI owner Yusuf; API toggle keeps Version 1 payloads unchanged.
